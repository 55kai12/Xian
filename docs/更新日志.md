## v2.0.61（2026-09-15）

用户原话：「回退版本」（在试用 v2.0.60 之后）。

**这一版的内容 = 完整回退掉 v2.0.60，与 v2.0.59 的代码状态逐字节一致。**

### 回退了什么

v2.0.60 为修「右划返回太敏感」动了两处，用户实测后认为不可接受，整体撤销：

1. `SwipeInterceptorLayout` 的横划判据由 `abs(dx) > abs(dy) * 0.5f` 改回原样
   —— 恢复成「横向位移超过纵向的一半就算横划」。
2. `View.setSystemGestureExclusionRects()` 对左右各 24dp 窄条的手势排除**整体移除**
   —— 屏幕左右边缘恢复系统「返回」手势。

回退方式：`git revert 3a022ea`（v2.0.60 那次提交），生成提交 `4e3a42d`。
不删历史，v2.0.60 的改动与撤销理由都留在 git log 里可查。

### 版本号为什么是 2.0.61 而不是 2.0.59

代码内容确实回到了 2.0.59，但**版本号必须往上走**：

- 手机上已装 `versionCode 260`，Android 拒绝降级安装
  （`INSTALL_FAILED_VERSION_DOWNGRADE`），发 259 的包会直接装不上。
- 因此把 `versionCode` 定为 261、`versionName` 定为 `2.0.61`
  ——「内容等于 2.0.59 的一个新版本」。

**以后回退版本一律按这个规则**：代码回退，版本号继续递增。

## v2.0.59（2026-09-15）

用户原话：「卡在锁机定时 / 立即锁机」

顺着上一版「在白名单里还被卡住」继续往下挖，把**退出锁机**整条链路上四个各自独立、
症状却长得一模一样的坑一次填掉。四个坑的共同点是用户看到的是同一句话
——「卡在锁机里出不去」，但成因完全不同，只能分开修。

### ① 定时时段每结束一次，偷偷扣掉一次退出额度（最要命的一条）

用户说的「定时锁机 / 立即锁机都卡」，真正的源头在这里。

`LockAlarmReceiver` 收到 `ACTION_END`（时段结束闹钟）时调的是 `LockMachineService.stop()`，
而这条路的入口第一件事就是 `LockExitQuota.consume()` —— **扣一次月度退出额度**，
还把这次记成「主动退出」（`heldOut = false`）。

时段结束明明是**自然到期**，一分额度都不该扣。而且它一定会扣到：
`applyAlarms` 排的结束时刻是「开始时刻 + 时长」，真正生效的结束时刻却是服务启动时
自己写的 `now + 时长`（`now` 比闹钟晚零点几秒），所以闹钟响的那一刻 `isActive`
往往还是 true —— 一次不落地扣。

额度只有 2 次/月：设一个每天晚上的时段，两天就扣光了。扣光之后 `stopLock()` 第一道关
就是 `consume()` 失败 → 只弹一句 Toast → **服务不停、状态不清、层不撤**。
用户从此退不出任何一次锁机，不管这次是定时来的还是手动「立即锁机」来的。

**修法**：`ACTION_END` 只负责重排下一个周期的闹钟，不再调 `stop()`。收尾本来也不需要它做 ——
时间一到，服务自己那个每秒循环的 `isActive` 变 false 就会退出循环、记一次「忍住了」、
清状态并撤层（`finishLock()`）。

### ② 覆盖层自己抢焦点，把锁机层判成「该让开」

系统为「本进程的悬浮窗抢到焦点」补发的那条窗口事件，包名是**贤自己**。
`FocusLockAccessibilityService` 上半段原先只对限额层做了特殊处理
（`packageName == 自己 && AppLimitOverlayController.isShowing()`），锁机层漏了 ——
于是这个包名被当成「用户切到了贤」写进 `ForegroundApp`，而贤自己在所有放行判断里都算通过。
后果：层刚 addView 上去，下一秒自检就判定「该让开」，层被自己撤掉；
用户切到别的应用也不盖，锁机形同虚设。

**修法**：条件扩成 `selfOverlayShowing()`（限额层 **或** 锁机层显示中都算）；并在下半段
放行判断的最前面加一条 —— 「包名是自己 且 自己的层正显示着」的事件**直接不作数**，
交给锁机层自己每秒的判定（那条路读系统使用记录，不受这条事件影响，一秒内给出正确答案）。
原来「靠 350ms 防抖吞掉自事件」的隐式依赖就此去掉，`hide(force = !selfEvent)` 简化成 `force = true`。

### ③ 用户点白名单图标、点「回到贤」，层不让开

这两个动作都是**用户明确的意图**，可原来两处都只做了 `startActivity`，然后指望
「无障碍事件跟上来把层撤掉」。感知断了（无障碍没开 / 服务被 ROM 清掉 / 使用记录没授权）
这条路就永远不来 —— 用户看到应用启动了、遮罩还盖在上面，也就是「明明在白名单里却被卡住」。

**修法**：两处都改成先 `ForegroundApp.mark(目标包名)` 再 `hide(force = true)`，然后才启动。
`mark` 顺手补一条「我确定用户去了这个包」，锁机层每秒的自检和守护服务的补盖都读它，
所以层不会在下一秒又被盖回来。

### ④ 退出被额度拦下时，界面上一句解释都没有

`exitNow()` 走不通时只弹一个 Toast，冷静期弹窗原样留在屏幕上、按钮看着还能点 ——
用户点完「确认退出」什么也没发生，这就是最直观的「卡住」。
锁机层上那行额度也只在显示「本月剩余退出次数：0 / 2」，看不出「这个月真的不给退了」。

**修法**：额度用完时把话写进冷静期弹窗里（并停掉它的每秒刷新，免得下一秒被倒计时覆盖回去）；
锁机层与锁机页的额度文案在 0 次时改用 `exit_quota_exhausted` 那句直白的话。

**顺带修**：`finishLock()` 原来无条件按 `heldOut = true`（忍住没退）记一笔 ——
可用户主动退出时（`stopLock()` 已按 `heldOut = false` 记过、并清掉了结束时刻），
服务循环退出后还会再记一笔「忍住」。现在按 `endAt > 0` 区分：留着结束时刻的才是自然到期。

**边界（要跟用户讲清）**：月度额度 2 次仍然只算**主动退出**。修完 ① 之后，定时时段来回滚
不再消耗额度，正常用一个月基本用不完。真被额度拦下时界面会明说，此时唯一出路是等这次锁机
跑到结束时刻（时段结束 / 立即锁机时长走完）—— 贤自己永远在白名单里，
锁机层上点「回到贤」随时能进来取消时段设置。

**发布**：`2.0.59 / 259`；签名 v1 + v2 通过，SHA-256 `f675510a…` 与既有一致；
旧包归档 `贤-2.0.58.apk`。


## v2.0.58（2026-09-15）

用户原话：「还是那个问题，我明明在白名单的应用里面，他没有监控到，还是会在锁机页面，卡住不让我用。」

**根因**：前台感知只有**一个**数据源 —— 无障碍服务的窗口事件。v2.0.54 加的 `sync()`
（起锁前先问「前台是不是白名单应用」）读的就是这个源，源一断它就等于白问：

1. 无障碍没打开 / 被系统重启后没接上 / 被 ROM 清掉 ⇒ 该值恒为 `null` ⇒ `sync()` 按「未知就锁」处理 ⇒ **照盖**；
2. 层盖上来那一刻，系统补发的窗口事件包名是**贤自己**（自己的悬浮窗抢了焦点），
   走到 `isAllowed(自己) = true` 分支后 `hide(force = !selfEvent)` = `hide(force = false)` ——
   被 350ms 防抖吞掉，层就停在用户脸上不动了；
3. 层盖着的时候，让开完全靠「无障碍事件」再送一条白名单应用的包名进来。源断了就**永远没有人来让开**，
   用户被彻底卡住，唯一出路是长按退出（冷静期 30 秒 + 密码 + 每月 3 次额度）。

**修法：给前台感知加第二数据源，并让覆盖层自己每秒对一次账，不再单靠事件驱动。**

- **新增 `UsageForeground`**：读系统使用记录（`UsageStatsManager.queryEvents`）判定前台应用。
  只要授予了「使用情况访问」就能读，**不依赖任何服务活着**。游标式增量查询（首次回溯 12 小时、
  之后每次只查新事件并留 5 秒重叠），息屏期间返回 `null` 但**不清**最后那个应用 ——
  亮屏解锁往往停在息屏前那个应用里，而系统不一定补发 resumed 事件，清掉就会被误判成「不知道」。
- **`ForegroundApp` 改造**：加 `mark()` / `resolve()` 与 8 秒信任期。窗口事件新鲜（8 秒内）直接用，
  零成本；不新鲜或为空时退回 `UsageForeground` 查一次。写入方仍只有无障碍服务。
- **锁机层每秒自检**（`tickRunnable`）：前台在白名单里就 `hide(force = true)` 立刻让开，
  不依赖任何窗口事件到达。这一条同时解决上面 ② 和 ③。
- **`LockMachineService` 每秒补盖**：只在**层没显示时**做，负责「用户从白名单应用切到别的应用」
  这个方向 —— 层显示着的时候它自己会自检，不用重复跑。
- **退出流程期间不对账**（`cooldownEndsAt > 0` 时跳过）：冷静期弹窗 / 密码面板开着时用户正在跟这层交互，
  输入法一弹出来前台就变成输入法，而输入法是永远放行的系统组件 —— 少了这道闸，
  用户刚长按完「退出锁机」整层就没了。
- **锁机页权限卡**：两个按钮变三个，补上「使用记录」（原来只有悬浮窗 / 无障碍，
  用户根本不知道还有第二个源）；下面加一行**前台感知状态**，
  显示当前走的是哪个源，两个都没有时显式提示「⚠ 白名单可能失效」。

**边界（要跟用户讲清）**：两个源都没有时（无障碍没开 **且** 未授予使用情况访问），
前台是谁无从得知，白名单必然失效 —— 这时锁机页那行提示会亮出来。至少给一个源即可正常工作。

**发布**：`2.0.58 / 258`；签名 v1 + v2 通过，SHA-256 `f675510a…` 与既有一致；
zip 完整（895 条目）；旧包归档 `贤-2.0.57.apk`。

## v2.0.55（2026-09-15）

用户追问「趋势线你完善好了吗」。这一版把 v2.0.53 只堵了一半的统计口径彻底收口，并顺手修掉曲线本身的形状误导。

### 一、统计口径收紧：清单里看不见的完成记录，一律不计

v2.0.53 只加了 `TaskSkipStore` 过滤（「仅删除该事件」），漏了三类幽灵记录中的两类。现在把判据统一成一句话：**一条完成记录，只有它在任务清单里真的能被看见，才计入统计**。

新增 `FocusRepository.visibleCompletions(allTasks, skipped)`，`getFocusStats()` 与 `getDailyCountsBetween()` 共用它，替换掉原先各自写的 `isCompleted && !isRepeatTemplate()` 过滤。判定函数 `completionIsVisible`：

1. **重复任务模板**（`templateId == 0 && repeatRule != none`）：残留的 `isCompleted = true` 是历史脏值，模板本身从不代表「完成过一次」；
2. **「仅删除该事件」**：`TaskSkipStore` 里记过这天的快照不再计数（v2.0.53 已有，这里并入同一处判定）；
3. **规则改过 / 模板已删**：快照日期必须仍落在模板当前规则的覆盖范围内（`RepeatRule.covers`）——这是本轮补上的关键一条。把「每天」改成「每周」，原来的周二/周三/周四快照仍然 `isCompleted = true` 躺在库里、`dueDate` 也仍在统计区间内；而清单里的快照由模板带出，带不出来的那几天**永远不显示**。于是「界面上没有、趋势线上有一笔」，用户看到的就是「任务删了它还算」。

配套修复：

- `getFocusStats()` 原先完全没有 `TaskSkipStore` 过滤 —— 番茄钟页的「今日贤时 / 近七日」比趋势线多算。现补 `skipped` 参数，`StatsViewModel.loadStats()` / `refresh()` 都传 `TaskSkipStore.all(context)`。调用方（`ReviewFragment` / `TimerFragment`）走的都是 `StatsViewModel`，无需改动。
- 新增 `RepeatRule` object 作为「这一天适用这条重复规则吗」的**唯一**判定，`TasksFragment.matchesRepeat` 改为委托它。原先清单和统计各写一份，这次正好是漏改统计侧导致的，所以顺手合并掉这个漂移点。
- `FocusRepository.startOfToday()` 改为 `startOfDay(System.currentTimeMillis())`，抽出 `startOfDay(timeMillis)`；模板起始日一律归零到当天 0 点再比较，避免模板的 `dueDate` 带时分秒时「同一天也算 `day < start`」而被误判为不可见。

⚠️ 口径变化会让「累计贤时」里的任务部分**变小**（被删掉的完成记录不再计入）。这是有意为之：记的是「当前清单的真实完成情况」，不是「历史上一共勾过多少次」。番茄钟时长 `totalMinutes` 不受影响（那本来就跟任务无关）。

### 二、曲线形状：消除 Catmull-Rom 过冲

```kotlin
private var foregroundPackage: String?
```

```kotlin
}
```

### 二、`hide()` 的防抖不再吞掉「该收起来」的判断（`force` 参数）

`hide()` 里那个 350ms 防抖只服务于一个目的：新层 `addView` 的那一瞬间，系统会为我们**自己的悬浮窗**补一个窗口事件，包名就是本应用 —— 而 `isAllowed(自己) == true`，不拦的话层会把自己撤掉。

问题在于它把「用户真的切进了白名单应用」也一并吞了：那种事件如果落在防抖窗口内（典型场景：某个系统弹窗刚把层顶起来、200ms 后白名单应用重新拿到前台），`hide()` 直接 return，层就留在白名单应用上面不动。

改成显式区分：

```kotlin
fun hide(context: Context, force: Boolean = false) {
    if (!force && System.currentTimeMillis() - lastShowAt < DEBOUNCE_MILLIS) return
    ...
}
```

调用侧由「谁在调用」决定要不要绕开防抖：

- 无障碍服务里，切到白名单应用 → `hide(force = !selfEvent)` —— 只有包名是本应用的自事件才允许被防抖拦下；
- 锁机结束（`stopLock` / `finishLock` / 判定到已不 active）→ `hide(force = true)`，那是确定该收的场景。

### 三、白名单列表不再每次事件都重建（卡顿来源）

```kotlin
if (whitelist.sorted().hashCode() == whitelistSignature) return
whitelistSignature = whitelist.sorted().hashCode()
```

指纹在层被 `hide()` 时重置为 -1，保证新建的层一定会建一次列表。

### 四、白名单展开加过渡


60 秒内再打开是秒开。

## v2.0.51（2026-09-14）

用户反馈：「删了后台还是不行」—— 连带上一版的 UsageStats 改造也没起效。逐层复核整条链路后，定位到**三条叠加的根因**，都属于「进程被清掉之后没有任何自救机制」，逐条修复。

### 根因一：被清掉之后没人把它拉回来（主因）

`GuardService` 上一版只声明了 `START_STICKY`，实证在国产 ROM 上形同虚设 —— 从最近任务划掉贤时，进程被直接杀死，**没有任何回调、没有闹钟兜底**，服务就此永久消失，直到用户下次手动打开贤。限额的记账与拦截都挂在它身上，于是「划掉后台就失效」。

修法（三重自救）：

- `onTaskRemoved`：趁进程还活着时排一个 1.5 秒后的闹钟，把自己重新拉起。
- `onDestroy`：若 `needsGuard` 仍成立（说明是被系统回收而非用户主动关功能），同样排闹钟复活；用户主动清空限额/时段时不排，不会赖着不走。
- `onStartCommand`：每次启动顺延一个 15 分钟的不精确闹钟做兜底，覆盖「进程被内存压力直接 kill、连 onDestroy 都没走」的情况。

闹钟用 `AlarmManager.setAndAllowWhileIdle`，**不用精确闹钟** —— 后者在 Android 12+ 需要用户另外授予「闹钟和提醒」权限，不值得为一个自检去要；不精确只是晚几秒到几十秒，而记账是游标回溯的，晚到的时间照样补得回来。从闹钟里启动前台服务属于 Android 12+ 的后台启动限制范围，`SYSTEM_ALERT_WINDOW` 在官方豁免名单里，本应用必然持有（限额层要显示），可以放心调。

### 根因二：记账只有守护服务一个驱动源

上一版把记账搬到 `AppLimitWatcher` 后，在无障碍那边写了 `if (AppLimitWatcher.isRunning()) return` —— 它活着时无障碍完全不出手，**但反过来守护服务掉线时，无障碍也不会接管**（守护服务刚死的那 6 秒内另一个源也不会顶上），整条链只剩一个支点。

修法：无障碍 tick 里增加一条 —— 守护服务掉线**且**用户已给「使用情况访问」时，由无障碍继续驱动**同一个** `AppLimitWatcher`。它是游标式的，谁驱动都不会重复计，天然可以多源驱动（这正是当初写游标的意义）。只有连「使用情况访问」都没给时，才退回原来那条依赖窗口事件的老路。

### 根因三：多源驱动时会把零头丢光

`credit()` 里是 `(to - from) / 1000` 直接截断。单一驱动源时每段 2 秒还好；两个源交错后段长常常是 0.5 秒、1.2 秒这种非整秒，**逐段各自截断会把零头全部丢掉**，一小时能少记十几分钟。改为毫秒累加器 `pendingMillis`，攒够 1 秒才写一次。

同时修掉一个会静默吞掉整段时间的判定：原 `tick()` 里 `if (from == 0L || now <= from || ...) { reset(); return }`，`now <= from` 在两源同毫秒各调一次时会成立，被误判成「墙上时间被拨回去」，每次都重走 reset 而不记账。改为严格小于 `now < from`。

### 附带修复

- `BootReceiver`（开机 / 覆盖安装）补 `GuardService.sync()` —— 覆盖安装会把 AlarmManager 的闹钟连同常驻服务一起清掉，不重建的话限额与定时锁机会静默失效到下次手动打开应用。
- `FocusLockAccessibilityService.onServiceConnected()` 在运行时补上 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`（覆盖安装后系统会按旧配置派发事件）。`capabilities` 是只读的、运行时改不了，这点已实测确认，所以「重开一次无障碍开关」的提示仍保留。
- 无障碍服务被系统重新拉起时顺手 `GuardService.sync()`，把记账的支点一起带回来。
- 限额页状态行新增一种状态：**「计时已在跑，但还没给使用情况访问：划掉后台就会停」** —— 点击直达授权页。之前这种情况显示「计时已就绪」，等于把最大的坑藏起来了。

## v2.0.50（2026-09-14）

**换数据源：应用限额不再依赖无障碍窗口事件，改读系统使用记录。**

用户反馈「一点用都没有，开着不行，删后台也不行」。复查整条链路（事件 → 前台应用 → `addSeconds` → 覆盖层）代码逻辑本身是通的，
问题在**数据源选错了**：窗口事件只在我们的进程活着、且系统愿意派发时才会到。
国产 ROM 一旦冻结 / 清掉进程（划掉最近任务、息屏、后台省电），事件就断 ——
表现就是播放两小时一秒都不记、划掉后台再也拦不住。这不是某个小 bug，是架构层面的脆弱。

- **新增 `AppLimitWatcher.kt`**：前台应用改从 `UsageStatsManager.queryEvents` 读（数字健康用的同一份系统记录）。
  - 游标式记账：记下「账已算到哪一刻 + 那一刻起前台是谁」，每 2 秒把新事件按时间顺序走一遍，
    逐段把时长记到对应应用头上。**记账精度由事件时间戳保证，与轮询频率无关。**
  - 进程被冻结 / 睡过去再醒来，`queryEvents` 会把这段时间的事件全部返回 ⇒ **补算回来**，
    这正是窗口事件做不到的。
  - 查询窗口往前多要 3 秒（`QUERY_OVERLAP_MILLIS`），规避系统事件入库延迟导致的漏读。
  - 息屏记作一次「变化（前台 = null）」，否则最后那个应用会被一路算下去。
  - 断档超 1 小时、墙上时间被往前拨：不对账，从此刻重新开始（宁可少记不可虚增）。
  - 限额层盖着时**不记账**（用户被挡在外面，没在玩）—— 否则加时白加。
- **`GuardService` 驱动记账**：限额列表非空时每 2 秒 tick 一次。它本来就为「划掉后台不被清」而常驻，正好兼任。
- **无障碍计时降级为后备**：`FocusLockAccessibilityService.tickAppLimit` 开头加
  `if (AppLimitWatcher.isRunning()) return`。两个来源**互斥**，同时算会把时长翻倍；
  用「最近一次 tick 的时刻」当心跳（6 秒），谁活着谁干，谁死了另一个自动顶上。
  没给「使用情况访问」权限的用户，行为与之前完全一致。
- **`AndroidManifest.xml`**：声明 `PACKAGE_USAGE_STATS`（`tools:ignore="ProtectedPermissions"`）。
  特殊权限，仍需用户在「使用情况访问」里手动授予。
- **限额页新增引导卡**：没给权限时显示「建议开启使用情况访问」，点击直达系统设置；
  状态行按「两条来源是否可用」分别提示，缺哪条就点哪条去补。
  「无障碍提示卡」与状态文案改为说明两条来源的关系。

## v2.0.49（2026-09-14）

**新增：守护前台服务（`GuardService`）—— 划掉后台后保护不再失效**

- 症状：从最近任务划掉贤之后，应用限额再也拦不住（像「删了后台就失效」）。
- 根因：应用限额的计时与拦截都跑在无障碍服务里，而**国产 ROM 会随「划掉后台」清掉进程**
  （部分直接 force-stop）。force-stop 会一并清掉 AlarmManager 里的所有闹钟，
  所以连 `LockHealthMonitor` 的 30 分钟体检也一起没了 —— 应用侧没有任何手段自救。
- 唯一有效的手段是**别被清**：有前台服务的应用不在这类清理名单里。新建 `GuardService`，
  只要还有「需要一直盯着」的东西就常驻：
  `AppLimitStore.limitedPackages().isNotEmpty() || LockMachineScheduler.isEnabled()`。
- 通知走 `IMPORTANCE_MIN` 渠道（不进状态栏、不发声、不亮屏），文案见 `guard_notification_*`。
- ⚠️ `onStartCommand` **先无条件 `startForeground` 再判断条件**：从 `startForegroundService`
  进来却没能及时转前台，会直接抛 `ForegroundServiceDidNotStartInTimeException`。
- 返回 `START_STICKY`：被系统按普通方式回收后自动重建（重建时 intent 为 null，会重新自检条件）。
- 启动点（必须都是**前台时机**，Android 12+ 不允许后台启动前台服务）：
  `MainActivity.onStart`、`AppLimitFragment.refresh`（覆盖增删应用与改额度）、
  `LockMachineScheduler.schedule/cancel`（时段变化）。`GuardService.sync()` 幂等，多调无害。
- manifest 加服务声明，`foregroundServiceType="specialUse"` 照 `LockMachineService`。

**还差一步，但这步应用做不到**：若划掉后台仍失效，说明那个 ROM 是真 force-stop 而非普通清理 ——
那是 Android 的设计，任何应用都无法自启。需要在系统设置里把「贤」加进**自启动白名单**，
并从最近任务里**锁定**它（MIUI 长按卡片上锁）。设置页已有自启动引导入口。

## v2.0.43（2026-09-14）

### 应用限额：额度用完后不弹窗 / 退出重进照样放行

**症状**：额度明明用完了，玩的时候只是闪一下（甚至没察觉），退出应用再点进去完全不被挡。

**根因**：限额覆盖层是本进程的悬浮窗，`addView` 之后它会抢到焦点，系统随即发一条
`TYPE_WINDOW_STATE_CHANGED`，**包名就是 `com.xian.focus` 自己**。
无障碍服务的事件处理里，只要包名不是状态栏、不是输入法这类系统组件，就无脑写进
`foregroundPackage` —— 于是下一秒 tick 里 `AppLimitStore.isLocked(context, "com.xian.focus")`
是 `false`，直接走 `AppLimitOverlayController.hide()`，**把自己刚盖上去的那一层撤掉**。
更粘的是：被写脏的前台应用记录还有 60 秒「事件信任期」，这 60 秒里 tick 一直以为
「前台是贤自己」，既不记时也不弹窗 —— 所以退出再点进去照样能玩。

**改法**（两处，都在根上）：

1. `FocusLockAccessibilityService.onAccessibilityEvent`：包名是自己的**且限额层正在显示**时，
   不再把它当「用户切到了贤」，而是清空前台缓存、放开查窗口的限频，让 tick 自己查一次窗口栈。
   - 层还盖着 → 查不到活跃的**应用**窗口（悬浮层在无障碍里属于 `TYPE_SYSTEM`）→ 沿用上次的

## v2.0.42（2026-09-13）

### 定时锁机：多时段 + 跨日提示 + 保存即自检；白名单改成独立设置

**1. 跨日锁机有明确说法了**
`23:00 → 07:00` 这种时段，页面上写成 **`23:00 → 次日 07:00`**；锁机运行中在倒计时下面
多一行「预计结束：明天 07:00」。以前只写 `23:00 - 07:00`，很容易被当成当天早上七点结束，
看起来就像设置没生效。

**2. 定时锁机支持任意多个时段**
`LockMachineScheduler` 从「一组 start/end」改成**时段列表**：每个时段排「开始」「结束」两个
闹钟，requestCode 按时段下标分配（开始 1001+，结束 1101+）。旧版单时段数据在第一次读取时
自动迁移成一个时段，用户无感。

时段编码用 `1380-420`（一天中的第几分钟），**跨日直接由 `end <= start` 表达**，
不需要额外字段，也不会出现「结束时间必须大于开始时间」的假限制。时长 = `(end-start+1440)%1440`。

设置页改成时段列表 UI：每行显示时段文案，点行改时间、点 ✕ 删除；下面是「＋ 添加时段」。
新增时段默认 22:00→23:00。草稿与已保存列表不一致时提示「有未保存的修改」，编辑完要按保存。

**3. 保存定时后立刻自检（用户报的「设了 23:23 不跳锁机」）**
根因：`applyAlarms` 只负责排下一次闹钟，而它会把**已经过去的开始时刻顺延到明天**。
23:26 保存一个 23:23 开始的时段，就会干等一天 —— 用户看到的就是「设了不生效」。
现在 `schedule()` 之后立刻调 `resumeIfInScheduledWindow()`：此刻若已落在某个时段内，
当场开始锁机（剩余时长按剩余时段算），并提示「当前正处在锁机时段内，已立刻开始锁机」；
没命中则提示「已保存，下次锁机：明天 23:23」，让用户知道为什么没立刻锁。

**4. 白名单改成独立持久设置（用户报的「完成锁机后白名单没了」）**
根因：`LockMachineController.start()` 会把白名单一起写进 prefs，也就是说
**只有「开始锁机」那一刻选的才会生效**。用户改完白名单却没点开始、或只保存了定时时段，
一重建视图（切页/转屏/返回）这份选择就白选了，界面上就是「白名单莫名其妙没了」。

现在读写拆开：`start(context, durationMinutes)` 只记起止时刻，白名单由

任何启动路径都不可能再冲掉它。`whitelist()` 改为返回副本，避免调用方改动污染内存里那份。
锁机运行中改白名单，覆盖层里的文件夹会立刻刷新。

**连带改动**：`LockMachineService.start()` 去掉 whitelist 参数（原来是定义了但根本没人读的
EXTRA_WHITELIST）；新增 `TimeLabels`（今天/明天/后天 HH:mm）供设置页和覆盖层共用，
避免两处各写一份「明天」的判断。

## v2.0.41（2026-09-13）

### 任务左划改成「露出四个动作按钮」，不再是滑走即删

**改成什么**：左划任务行，露出四个色块按钮，点哪个执行哪个 ——
① 完成（青绿）② 上移一行（蓝）③ 下移一行（橙）④ 删除（红）。

**为什么不能再用 ItemTouchHelper 的 swipe**
它只有两种结局：滑过阈值 `onSwiped` 回调（等于「划走」），或没滑过阈值回弹归位。
「松手停在中间、等用户点按钮」它表达不了 —— `ACTION_UP` 时它会把 `translationX` 补间回 0，
露出来的那一瞬间就被收走了。所以横向手势必须自己管。

**新增 `SwipeActionLayout`**（FrameLayout 子类，约 150 行）
- 子 View 约定：0 = 动作行（停靠右侧），1 = 内容层（铺满）。横向拖动移动内容层，露出下层动作行。
- 拖动超过 `touchSlop` 且横向位移大于纵向才接管，纵向留给 RecyclerView 滚动；
  接管后 `requestDisallowInterceptTouchEvent(true)` 防止父容器抢走。
- 松手超过半个动作区就吸附到展开位，否则弹回；吸附动画用 `ValueAnimator` 手写
  （`ViewPropertyAnimator` 在 cancel 时回调时机不可靠，会和拖动抢 `translationX`）。
- 动作行宽度按可用宽度算：`min(可用宽度 × 0.6, 4 × 64dp)`，不写死 dp。
- 测量顺序：先量内容层，再用它的高度 `EXACTLY` 量动作行 —— RecyclerView 传的是 UNSPECIFIED，
  反过来量色块撑不满整行。

**`item_task.xml`**：根从 `MaterialCardView` 改成 `SwipeActionLayout`，里面套一层
`MaterialCardView` 作内容层，右侧加四个 `ImageView` 动作块（`ic_swipe_done` / `ic_swipe_up` /
`ic_swipe_down` / `ic_delete_task`，白图标压饱和色块）。新增四个功能色（不随昼夜翻面）。

**四个动作的接法**
- 完成 → 复用 `onToggleTask`（`toggleComplete`）。
- 上移 / 下移 → `moveTaskRow(task, ±1)`：只在同一完成态区域内交换，和拖拽排序规则一致。
  **写回时只把 `templateId == 0` 的真实行交给 `reorderTasks`** —— 列表里的重复任务行是
  「模板行的当天副本」（id 就是模板 id、`dueDate` 被改成了当天），整行写回会把模板的起始日期
  一起改掉，而 weekly / monthly 的判断锚点正是它。所以按系列 id 映射回真实模板行再重排。
- 删除 → 新增统一入口 `deleteTaskWithConfirm`：普通任务直接删，重复任务走四档询问。

**`ItemTouchHelper` 只留拖拽排序**（swipe 方向传 0），删掉 `onChildDraw` 的红底绘制、
`onSwiped` 的删除分发和 `restoreSwipedRow`；`onSwiped` 仍需空实现（抽象方法）。
展开的行在「滚动 / 开始拖拽排序 / 点内容想编辑」时自动收起，同一时刻只留一行展开。

**一处踩坑**：`SwipeActionLayout.onTouchEvent` 原先在非拖动时也 `return true`，
结果 DOWN 不进入按下状态、UP 也没有 `performClick`，**整行点击进编辑会一起失效**；
改成非拖动时交回 `super.onTouchEvent`。

**已知取舍**：已完成的行滑出来第一个仍是「勾」图标，点它等于取消完成（行为和行内序号方框一致）。

**改动文件**：`SwipeActionLayout.kt`（新）、`item_task.xml`、`TaskAdapter.kt`、`TasksFragment.kt`、
`colors.xml`、`ic_swipe_done/up/down.xml`（新）、中英 strings。

## v2.0.39（2026-09-13）

### 修应用限额「用了不记录」

**根因：计时完全依赖窗口事件，事件一断就永久停摆**
- 「哪个应用在前台」原先只由 `TYPE_WINDOW_STATE_CHANGED` 事件的 `packageName` 喂给 `foregroundPackage`。
- 无障碍服务被系统重启（国产 ROM 常态）后这个缓存会清空；如果用户此时已经待在某个应用里、之后又没发生过应用切换，事件永远不会补发 —— `foregroundPackage` 一直是 null，一秒都记不上。表现出来的就是「用了一整天，一点记录都没有」。

**修复：加一条不依赖任何事件的兜底通道**
- 打开 `accessibility_service.xml` 的 `canRetrieveWindowContent` + `flagRetrieveInteractiveWindows`，让服务可以查窗口栈。
- 新增 `foregroundPackageForTick()`：缓存 60 秒内被事件确认过就直接用（零开销，正常路径完全不变）；过期或为空时，自己读一次窗口栈里 `TYPE_APPLICATION && isActive` 的窗口拿包名。主动查询限频 5 秒，不会每秒去翻窗口栈。
- 查不到包名就退回旧值，宁可记到旧应用也不漏记。

**顺带修掉三处会导致「少记」的隐患**
- `limitTicker` 里 `tickAppLimit()` 一旦抛异常，下一帧的 `postDelayed` 就不会执行，计时从此永久停摆 → 用 `runCatching` 兜住，保证 ticker 永不断。
- 计时改用 `SystemClock.elapsedRealtime()`（单调时钟）。原来用墙上时间，系统被 NTP 校准往回拨时差值为负，这一秒就凭空消失了。
- 不足一秒的零头攒着下次一起算（`pendingMillis`）。原来每秒一次整数除法丢掉几百毫秒，一小时能少记十几分钟。
- 息屏、系统休眠（两次 tick 间隔超过 10 秒）时既不计时也不留零头，避免唤醒后凭空多记 5 秒。

**限额页现在能看到「数字在涨」**
- 停在页面上时每 3 秒检查一次「最近计时时刻」，变了才刷新列表。原来只在 `onResume` 刷一次，用户根本分不清「没在计时」和「界面没刷新」。

> ⚠️ 本次改动了无障碍服务配置，装好后**需要把「贤」的无障碍开关关掉再打开一次**（或重启手机），让系统重新读取新配置。
> ⚠️ 因为要读窗口栈，系统设置里该服务的权限描述会变成「可以查看屏幕内容」。这是拿前台应用包名的必要代价，本应用不采集、不上传任何屏幕内容。

## v2.0.32（2026-09-13）

### 任务左划删除 + 重复任务的删除范围

**左划删除**
- 任务行左划即可删除，滑开时右侧露出红色「删除」底。
- 普通任务直接删；重复任务先弹窗问范围（见下）。
- 划开后若在弹窗里选了取消，行会原位放回，不会凭空消失。

**重复任务的四种删除范围**

列表里同一个重复任务有两种形态 —— 未完成时是「模板行的当天副本」（`id` 就是模板 id），完成时是「当天快照行」（`templateId` = 模板 id）。所以四种范围都以 `templateId`（为 0 时取 `task.id`）作为系列 id：

1. **仅删除该事件** —— 只让这一天不出现，别的日期和系列本身都不动。
   数据模型里模板行表达的是「每天都出现」，没有「唯独某天不要」的存储位，所以新增 `TaskSkipStore`：用 SharedPreferences 记一份 `<模板id>@<当天 0 点时间戳>` 的集合，构建当天实例时过滤掉。
   没为这一个动作去改 Room 表结构 —— 加排除表要连带一次数据库迁移，代价不成比例。
2. **删除全部该事件** —— 模板行连同它名下所有快照行一起删。
3. **删除全部该事件（保留已完成的）** —— 两步，顺序不能换：先把已完成的快照摘成普通任务（`templateId=0` **且** `repeatRule='none'`），再删模板与未完成快照。
   必须连 `repeatRule` 一起清 —— 只把 `templateId` 置 0 的话，`repeatRule != none && templateId == 0` 恰好就是「重复任务模板」的判定条件，这些本该躺在历史里的记录会被当成模板，从今天起每天重新冒出来。
4. **取消** —— 什么都不做，行已复位。

- `TaskDao`：`deleteTemplateWithSnapshots` / `detachCompletedSnapshots` / `deleteTemplateAndUnfinishedSnapshots`。

## v2.0.31（2026-09-13）

### 修复：完成任务后任务序号不刷新

**现象**
- 开启「显示序号」时，任务列表是 1 / 2 / 3。完成第 2 项后，剩下的两项序号没有跟着变成 1 / 2，仍然显示 1 / 3；切一次页面才补上。

**根因**
- 序号不是任务数据的一部分，而是 `TaskAdapter.submitTasks()` 现算的一张派生表 `unfinishedNumbers`（已完成恒为 0，未完成按顺序 1、2、3…），绑定时用 `unfinishedNumbers[task.id]` 取值。
- `ListAdapter` 的增量更新走 `DiffUtil`，而 `areContentsTheSame` 比较的是 `Task` 对象本身。完成第 2 项时，第 1、3 项的 `Task` 一字未改 → DiffUtil 判定「内容无变化」→ 不会重绑它们 → 序号停在旧值。切页面时 Fragment 与 adapter 整体重建、全量重绑，序号才正确。

**修复**
- `TaskAdapter.submitTasks()` 保存提交前的序号表，在 `submitList` 的 commit 回调里比对：只对序号真的发生了变化的行调 `notifyItemChanged`。
- 修在共同路径上，**顺带修好同一根因的另一处**：拖动排序后序号同样不会刷新（拖拽每次 `onMove` 都调 `submitTasks`，但 `Task` 内容没变，DiffUtil 只发 move、不重绑）。
- 只重绑序号变化的行，而不是整表 `notifyItemRangeChanged` —— 避免拖拽时反复全量重绑掉帧，也避免打断完成瞬间刚启动的划线展开动画。

### 一、锁机页显示当前时间

锁机覆盖层原来只有「还剩多久」，看不到现在几点。现在倒计时下方多一行「现在 HH:mm」，

### 二、退出锁机每月限 2 次

**规则**：每个自然月内主动退出锁机最多 2 次；**锁机自然到期不算退出，不消耗额度**。
跨月自动重置 —— 存的是 `年*100+月`，读的时候月份对不上就当 0 次，不需要定时任务去清零。

**唯一扣额度点**是 `LockMachineService.stopLock()`。所有主动退出路径 ——
覆盖层长按、通知栏「停止锁机」、应用内「停止锁机」按钮 —— 最后都汇进这个方法，

**UI 侧只做只读预检**。覆盖层长按和应用内按钮在发起退出前调 `canExit()`，
额度用完就地弹「本月退出锁机次数已用完（每月 2 次）」，不把退出请求发出去。
之所以拆成「预检只读 + 扣减单点」，是因为扣减必须在一处做原子判断 ——
UI 若也 consume，一次退出就会被扣两次额度。

**额度是可见的**：锁机覆盖层退出按钮上方显示「本月剩余退出次数：N / 2」，
锁机设置页状态区也显示同一行。一个看不见的限额只会让人在退不出去的时候更烦躁。

**顺带补的一个边界**：`stopLock()` 先判断锁机是否还在运行，不在运行就直接 `stopSelf()`，
不消耗额度 —— 否则在没有锁机的情况下误触发停止，会白白吃掉一次机会。

## v2.0.23（2026-09-12）

> 修一个用户实测报出来的重复任务 Bug：把任务改成「每日」后，后面每一天都显示已完成，
> 而且点取消也取消不掉，只有趋势线在动。

### 现象

1. 在某个日期的任务上打开编辑页，把重复规则改成「每日」，之后每一天都出现这个任务（这是每日重复的正常行为）。
2. 点一下完成，**后面每一天全都变成已完成**。
3. 再点想取消，**列表左边的方框还是 ✓、标题划线和灰字都没恢复**；只有下方趋势线数字在变。

### 根因：重复任务模板的 `isCompleted` 被当成了「完成态」

这个应用的重复任务是「**模板行 + 每日快照行**」模型：

- 模板行：`repeatRule != none` 且 `templateId == 0`，只描述「这个任务每天出现」，本身不该有完成态。
- 快照行：`templateId == 模板 id`，代表「某一天完成了」。

任务清单每天渲染时，对重复任务取 `task.copy(dueDate = day)` 生成虚拟实例 —— **这个 copy 会把模板自己的 `isCompleted` 一起继承下来**。

于是只要模板的 `isCompleted` 是 `true`：

- 每一天的虚拟实例都是 `isCompleted = true` → 全都被划掉、周条 7 天全满（现象 2）。
- 点「取消完成」走的是「删除当天快照」分支，删完拿出来的**还是继承自模板的 `true`** → 界面纹丝不动（现象 3）。
- 唯一会变的是趋势线，因为它直读数据库 —— 快照确实被删掉了（现象 3 的「只有趋势线变化」）。

### 模板的 `isCompleted` 是怎么变脏的

编辑对话框保存时执行的是 `task.copy(repeatRule = "daily", ...)`，**`isCompleted` 不在覆盖列表里，于是原值被原样保留**。
把一个「已经勾选完成的普通任务」改成「每日」，就把那个 `true` 一起写进了模板。

数据库里本来有一条同样的清理 SQL（`MIGRATION_8_9` 里 `UPDATE tasks SET isCompleted = 0 WHERE repeatRule != 'none'`），
但它**只在版本升级时跑一次**，管不了之后新写进来的值 —— 用户手机上那条脏模板就是这么来的。

### 改法：让「模板永远未完成」成为数据层不变式

| # | 位置 | 改动 |
|---|------|------|
| 1 | `data/FocusRepository.kt` | 新增 `normalizeRepeatTemplate()` / `isRepeatTemplate()`；`insertTask` / `updateTask` / `updateTasks` 写入前统一归一化，**重复任务模板一律清成未完成** |

### 一、修复会丢数据的功能缺陷

**1. 重复任务选「没有日期」后从列表里彻底消失**

- 位置：`TasksFragment.buildOccurrencesForDay()`
- 原逻辑：`val start = task.dueDate ?: continue`，没有起始日期就直接跳过整条任务。
- 后果：任务在任何一天都不显示，用户既看不到、也勾不掉、更删不掉，成为一条死数据。
- 修复：重复任务缺日期时以**创建日期**作为起始锚点（`createdAt` 归零到当天 00:00）。
  weekly / monthly 需要锚点判断星期几和几号，所以不能简单当作"每天"处理。
- 同时修复同类问题：**没有截止日期的普通任务**此前同样永不显示，现在归入「今天」列表。

**2. 编辑任务会清空所有子任务完成状态**

- 位置：`TaskViewModel.updateTaskWithSubtasks()`
- 原逻辑：先 `deleteSubtasksByTaskId()` 删光，再逐条重插，而 `Subtask.isCompleted` 默认 `false`。
- 后果：用户哪怕只改一个标题，所有已勾选的子任务都会被静默重置，无任何提示。
- 修复：按标题配对已存在的子任务并保留完成状态（同名标题按出现顺序逐个消费），再重建。

**3. 「自定义锁机时间段」只生效一次**

- 位置：`LockAlarmReceiver`
- 原逻辑：`AlarmManager.setAlarmClock()` 是**一次性**闹钟，触发后没有重排。
- 后果：时间段只在设置当天生效，第二天起再也不锁，除非重启手机或重新保存一次设置。
- 修复：`ACTION_START` / `ACTION_END` 触发后立即调用 `LockMachineScheduler.applyAlarms()` 重排下一天。
  另外在 `applyAlarms()` 里加了 1 秒安全余量，避免闹钟刚刚触发就被判定为"还未到"而在同一秒内反复自触发。

**4. 锁机状态只存在内存，进程被杀后静默失效**

- 位置：`LockController`
- 原逻辑：`lockEnabled` / `timerRunning` 是两个内存静态变量。
- 后果：用户在任务管理器里划掉应用，重新打开时锁机状态变回 `false`，遮罩消失 —— 这是锁机类应用最忌的绕过口。
- 修复：改为从持久化数据推导 —— 用户开关存于 `TimerSettingsPreferences`（落盘），
  番茄钟是否在跑读取持久化的 `TimerSession`。两者都不依赖任何存活的内存状态或界面。
- 同时明确：**暂停（PAUSED）依然算锁机生效**，否则按一下暂停就能临时解锁去刷别的应用。
- 并校验阶段结束时间，避免进程被杀后残留的过期 session 把用户永久锁在应用外面。

**5. 「清除所有数据」清不干净**

- 位置：`SettingsFragment.clearAllData()`
- 原逻辑：只清了 `focus_preferences` 和 `fortune_data`，然后 `deleteDatabase("focuslist.db")`。
- 后果：① 日记（`review_prefs`）、应用锁 PIN（`app_lock_prefs`）、主题、壁纸、锁机设置、
  分类配色、事件设置全部残留；② 直接删库文件时已打开的连接仍持有文件句柄，部分机型上"删了个寂寞"。
- 修复：停掉计时/锁机服务与闹钟 → 清空 **11 个** SharedPreferences（同步 `commit()` 确保落盘）
  → 改用 `clearAllTables()` 复用连接清空所有表 → 删除壁纸与导出缓存文件 → 用 `CLEAR_TASK` 重启界面。

**6. 番茄钟用 `delay(1000)` 递减，息屏时计时漂移**

- 位置：`TimerEngine.runCountdown()`
- 原逻辑：每 `delay(1000)` 把 `remainingSeconds` 减一。
- 后果：息屏 / Doze 会把协程的 `delay` 拉长，25 分钟的番茄钟实际可能跑成半小时以上，
  统计里记录的时长也和用户体感对不上。
- 修复：改为记录阶段结束的墙钟时间戳 `phaseEndAt`，剩余秒数由 `phaseEndAt - now` 反推；

  进程被杀重新拉起时也按墙钟重算剩余（阶段已走完则回到空闲，不凭空补记番茄钟）。

**7. 锁机遮罩没有系统豁免，会挡住来电话和输入法**

### 操作内容

### 具体步骤

2. **方案——只有 pull indicator 区域开始的触摸才允许拦截**：

1. 修复：将 `res/color/ripple.xml` 改为标准 ColorStateList：



```
\<selector xmlns:android="http://schemas.android.com/apk/res/android">

&#x20;   \<item android:color="#33FFFFFF" />

\</selector>
```



1. 检查 `default_text_color.xml` 和 `secondary_text_color.xml`，确认均为标准 `<selector>`，无同类问题。
