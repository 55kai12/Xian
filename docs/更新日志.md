## v2.0.28（2026-09-13）

> 新增「应用限额」：给应用定每日可用时长，用完当天锁死、次日自动恢复。入口在任务清单左上角抽屉里。

### 为什么要做

番茄钟和锁机管的是「某个时段不许玩」，管不了「今天总共别玩超过半小时」。
刷短视频这类行为是碎片化的，限时段对它基本无效，只有按**累计时长**设额度才管得住。
补上这一层：日常使用中计时，超限即锁，一天内不能再玩。

### 一、计时：AppLimitStore + 无障碍服务

- 用量**不读系统 `UsageStatsManager`**，而是由已有的 `FocusLockAccessibilityService`
  每秒把时间累加到当前前台应用头上。
  - 好处：**新增零权限**。走系统统计则要多申请「使用情况访问」这个特殊权限
    （只能跳系统设置页单独授权），体验差、用户容易漏授。
  - 代价：只在无障碍服务运行期间计时 —— 页面顶部显式提示，未开启时直接给开启入口。
- 前台应用从已有的 `TYPE_WINDOW_STATE_CHANGED` 事件取；输入法/状态栏等系统组件不算
  「在用某个应用」，保留上一个真实前台应用 —— 否则一打字计时就断了。
- **息屏不计时**（`PowerManager.isInteractive`）。少了这个判断，手机揣兜里放一晚，
  第二天额度莫名其妙就满了。
- 单次 tick 的补偿上限 5 秒，防卡顿/休眠恢复后一次补进一大段时间。
- 跨日清零挂在读写的必经路径上（`rollover()`），不依赖任何定时任务或闹钟：
  日期对不上就清空当日用量，限额配置保留。

### 二、超限上锁：AppLimitOverlayController

- 整屏遮挡层，`TYPE_APPLICATION_OVERLAY`，沿用锁机覆盖层那套配色法
  （品牌色铺底 + 半透明白元素）与 `ThemeStore.wrap`，跟随用户选的色相。
- 显示被锁应用图标 + 名称 +「每天可用 N 分钟，明天自动恢复」，并给一个
  「返回桌面」按钮 —— 被挡住了总得有条出路。
- 与锁机覆盖层互斥：锁机进行中不抢屏（锁机优先级更高）。
- 次日用量清零后由 ticker 自动移除，用户不需要任何操作。

### 三、入口与设置页

- 入口：任务清单左上角抽屉新增「应用限额」，与「倒数日」条目同构。
- 列表只列**已设限额的应用**：图标 / 名称 / 今日已用 ÷ 限额；
  已用完的显示「今日额度已用完，明天恢复」。
- 「+」添加应用：复用锁机的应用选择器（`WhitelistAppPicker` 增加了可传标题的参数，
  默认值保住原有两处调用点），新选中的默认 30 分钟/天；在选择器里取消勾选 = 取消该应用限额。
- 点某行改额度：15 / 30 / 45 / 60 / 90 / 120 分钟，或不限制。

### 四、改动文件

新增：`AppLimitStore.kt`、`AppLimitOverlayController.kt`、`AppLimitFragment.kt`、
`res/layout/fragment_app_limit.xml`、`item_app_limit.xml`、`overlay_app_limit.xml`。

改动：`FocusLockAccessibilityService.kt`（秒级计时 + 超限检测）、`WhitelistAppPicker.kt`（标题参数）、
`LockHealth.kt`（`isAccessibilityOn` 对外可见）、`fragment_tasks.xml` + `TasksFragment.kt`（抽屉入口）、
中英 `strings.xml`。

## v2.0.27（2026-09-12）

> 锁机数据接入统计页：回顾页新增「本月锁机」卡片（次数 / 时长 / 忍住没退）。

### 为什么要做

锁机数据此前**只有当下，没有历史** —— 系统里只存着本次锁机的结束时刻，
一次锁机结束后就什么都不剩了。锁机/退出额度（v2.0.25）改完之后，
「这月锁了几次、累计锁了多久、忍住没退几次」恰恰是用户最该看到的自我激励数据，却没有任何出口。

### 一、先把数据记下来

- `LockMachineController.start()` 现在同时记录**开始时刻**（此前只记结束时刻，
  实际锁了多久根本算不出来）；`elapsedMillis()` 按开始时刻到现在/结束时刻中较早者计算实际时长。
- `LockMachineService` 的两个结束点各记一笔，且都赶在 `stop()` 清掉开始时刻**之前**：
  - 自然到期（`finishLock`）→ **忍住没退**；
  - 额度内主动退出（`stopLock`）→ 普通一次。
- 新增 `LockStats`：与 `LockExitQuota` 同一套路 —— 按自然月聚合存 SharedPreferences，
  键带「年*100+月」，跨月自动重置，不需要任何定时清零。只存聚合值（次数 / 分钟 / 忍住数），
  不存逐次会话 —— 统计页要的就是这三个数，逐次记录属于还没有消费者就先建仓库。

### 二、统计页展示

回顾页在「累计 / 专注分钟」卡片下方新增一张「本月锁机」卡片，三列：
**次数、时长（≥60 分钟显示「X 小时 Y 分」，否则「Y 分钟」）、忍住没退**。

- 不走 StateFlow：锁机结束时统计页通常不在前台，StateFlow 同值不重发，
  回到页面会看到旧数。所以锁机统计在 `repeatOnLifecycle(STARTED)` 里每次直接读一次，
  保证每次回到页面都是最新值。

| `LockStats.kt` | 新增，本月锁机聚合统计 |
| `LockMachineController.kt` | 记开始时刻；新增 `elapsedMillis()` |
| `LockMachineService.kt` | 自然到期 / 主动退出两个结束点各记一笔 |
| `fragment_review.xml` | 新增「本月锁机」卡片（三列） |
| `ReviewFragment.kt` | 读快照并展示；时长格式化 |

## v2.0.26（2026-09-12）

> 退出锁机加 30 秒冷静期确认弹窗；锁机页的白名单应用收进一个「文件夹」。

### 一、退出锁机的 30 秒冷静期

**规则**：长按「退出锁机」后不再直接退出，而是弹一个确认窗 ——
30 秒冷静期倒计时走完之前，「确认退出」按钮是禁用的；走完了才能点。
随时可以点「继续锁机」关掉弹窗，不影响锁机。

**为什么必须连应用内按钮一起管**：贤本身永远在白名单里（`isAllowed` 硬编码放行自己的包名），
用户随时可以打开贤在锁机页点「停止锁机」。如果只有覆盖层走冷静期，
应用内这条 3 秒就能绕过的小路会把 30 秒冷静期变成装饰。
所以 `LockFragment.toggleLock()` 的停止分支也改成先弹冷静期对话框（`AlertDialog` + 每秒倒计时）。

**悬浮窗弹不了 AlertDialog** —— 它没有 Activity window token。
覆盖层里的确认窗是内嵌的一层全屏遮罩（`exitConfirmOverlay`，默认 GONE）：
外层布局包进 FrameLayout，遮罩 `clickable=true` 吃掉所有触摸，卡片样式复用半透明白语言
（新增 `bg_overlay_card.xml` + `overlay_scrim` / `overlay_confirm_card` 两个色）。
倒计时没有另起计时器，挂在覆盖层已有的每秒 tick 上。

**按钮主次是反直觉但刻意的**：「继续锁机」是实心主按钮在上，「确认退出」是禁用的描边按钮在下 ——
冷静期弹窗的场景里，正确选项应该更醒目。

**与额度（v2.0.25）的协作**：扣额度仍然唯一发生在 `LockMachineService.stopLock()`。
冷静期只是把「发起退出」这个动作拦在前面的闸门；确认按钮点击时才走
`canExit()` 预检 + 发起停止，额度语义没有变。

### 二、白名单应用收进「文件夹」

锁机页原来把白名单应用一列全摊开（每行一张卡片），应用一多就把整页占满。
现在默认只有一个文件夹卡片行：文件夹图标 + 「白名单应用」+「N 个应用」+ 展开箭头，
点开才显示应用列表（原来的卡片行原样保留），再点收起。

- 文件夹行和列表、空提示包在一个 `weight=1` 的容器里，
  **收起、展开、白名单为空三种状态下，底部按钮都稳定贴底**，不会跟着内容跳。
- 白名单为空时文件夹行整个隐藏，只显示「暂无白名单应用」。
- 展开状态不持久化：覆盖层每次重建都回到收起 —— 锁机页应该默认最安静。
- 原来的「锁机期间可用」小标题删掉，文件夹行本身就是标题。

## v2.0.25（2026-09-12）

> 锁机覆盖层显示当前时间；主动退出锁机改成每自然月限额 2 次。

### 一、锁机页显示当前时间

锁机覆盖层原来只有「还剩多久」，看不到现在几点。现在倒计时下方多一行「现在 HH:mm」，
跟倒计时共用同一个每秒 tick，没有额外起计时器。

用的是 24 小时制的 `Calendar.HOUR_OF_DAY`，**不跟随系统的 12/24 小时设置** ——
跟随系统要额外读 `DateFormat.is24HourFormat` 并处理 am/pm 文案，锁机页只是信息展示，先不引入。

### 二、退出锁机每月限 2 次

**规则**：每个自然月内主动退出锁机最多 2 次；**锁机自然到期不算退出，不消耗额度**。
跨月自动重置 —— 存的是 `年*100+月`，读的时候月份对不上就当 0 次，不需要定时任务去清零。

**唯一扣额度点**是 `LockMachineService.stopLock()`。所有主动退出路径 ——
覆盖层长按、通知栏「停止锁机」、应用内「停止锁机」按钮 —— 最后都汇进这个方法，
所以只在这一处 `consume()`：既不会漏掉某条路径，也不会一条路径扣两次。

**UI 侧只做只读预检**。覆盖层长按和应用内按钮在发起退出前调 `canExit()`，
额度用完就地弹「本月退出锁机次数已用完（每月 2 次）」，不把退出请求发出去。
之所以拆成「预检只读 + 扣减单点」，是因为扣减必须在一处做原子判断 ——
UI 若也 consume，一次退出就会被扣两次额度。

**额度是可见的**：锁机覆盖层退出按钮上方显示「本月剩余退出次数：N / 2」，
锁机设置页状态区也显示同一行。一个看不见的限额只会让人在退不出去的时候更烦躁。

**顺带补的一个边界**：`stopLock()` 先判断锁机是否还在运行，不在运行就直接 `stopSelf()`，
不消耗额度 —— 否则在没有锁机的情况下误触发停止，会白白吃掉一次机会。

## v2.0.24（2026-09-12）

> 重做锁机覆盖层（锁机时盖在屏幕上的那一层），倒计时换成翻牌时钟。

### 为什么要改

锁机覆盖层原来是一屏「系统默认灰按钮 + 一串橙色数字」，跟 app 的古风设计语言完全脱节；
倒计时只是每秒跳一个数字，没有反馈感。

### 一、视觉重做

**底色跟着主题走。** 覆盖层是 WindowManager 悬浮窗，只能用 `applicationContext` 渲染，
拿到的是清单里的默认主题 —— 也就是说无论用户在设置里选哪套色相，锁机页永远是青绿。
现在用 `ThemeStore.wrap()` 套一层 `ContextThemeWrapper`，铺底的主色和强调色跟设置里选的一致。

**配色只引入一个「半透明白」概念。** 铺底是当前主题的品牌主色，上面所有元素用半透明白叠加 ——
半透明白会和底下任何色相自动调和，所以 4 套主题 × 昼夜共 8 种组合不用各配一份颜色，
`values-night` 也不用再覆盖一遍。

**白名单从「一列系统灰按钮」变成可点的卡片行**：应用图标 + 名称 + 「打开」提示，圆角 14dp，按下有反馈。
白名单为空时不再留一块空白滚动区，改成居中显示「暂无白名单应用」。

**两个按钮区分主次**：「回到本应用」是白底 + 主题色字（视觉焦点），「长按退出锁机」是描边 + 白字（弱化）。

**入场淡入 220ms**，不再「啪」地一下盖上来。

**专注锁机那层（`overlay_lock.xml`）同步换成同一套语言** —— 它俩是同一场景的两个变体，只改一个会明显割裂。

### 二、翻牌倒计时

新增 `FlipClockView`：传 `"MM:SS"` / `"HH:MM:SS"` 字符串，数字位逐位翻页，`:` 画两个点。

- **逐位独立**：只有真正变了的那一位会翻。所以 25:30 → 25:29 只有最后一位动，
  01:00 → 00:59 会有三位同时翻。
- **翻转的实现**：卡片绕中间那条折线转 θ 角，投影高度就是 h·cosθ ——
  上半页倒下去（0→90°）、下半页翻上来（90→0°），两段各占动画一半时间。
  用 `canvas.scale` 在中轴上做垂直压缩就够了，不需要 Camera 的透视矩阵，代码少一半。
  代价是没有近大远小的透视感，翻牌的动作仍然清楚 —— 这是刻意的取舍。
- **时间格式留在调用方**：复用 `LockMachineController.remainingText()`，
  「超过一小时才显示小时位」这类规则不用在 View 里再实现一遍。

### 三、顺手修的一个隐患

悬浮窗的 `LayoutInflater` **不带 AppCompat 的 Factory2**，所以布局里的普通 `<Button>` 标签
**不会**被自动替换成 `MaterialButton`，`app:strokeColor` / `app:cornerRadius` 这类属性会被静默丢掉。
两个覆盖层的按钮都改写成全限定标签 `com.google.android.material.button.MaterialButton`，
并在布局里留了注释说明原因 —— 否则以后照抄 app 内布局的写法往这里加按钮，样式会莫名其妙不生效。

## v2.0.23（2026-09-12）

> 修一个用户实测报出来的重复任务 Bug：把任务改成「每日」后，后面每一天都显示已完成，
> 而且点取消也取消不掉，只有趋势线在动。

### 现象

1. 在某个日期的任务上打开编辑页，把重复规则改成「每日」，之后每一天都出现这个任务（这是每日重复的正常行为）。
2. 点一下完成，**后面每一天全都变成已完成**。
3. 再点想取消，**列表左边的方框还是 ✓、标题划线和灰字都没恢复**；只有下方趋势线数字在变。

### 根因：重复任务模板的 `isCompleted` 被当成了「完成态」

这个应用的重复任务是「**模板行 + 每日快照行**」模型：

- 模板行：`repeatRule != none` 且 `templateId == 0`，只描述「这个任务每天出现」，本身不该有完成态。
- 快照行：`templateId == 模板 id`，代表「某一天完成了」。

任务清单每天渲染时，对重复任务取 `task.copy(dueDate = day)` 生成虚拟实例 —— **这个 copy 会把模板自己的 `isCompleted` 一起继承下来**。

于是只要模板的 `isCompleted` 是 `true`：

- 每一天的虚拟实例都是 `isCompleted = true` → 全都被划掉、周条 7 天全满（现象 2）。
- 点「取消完成」走的是「删除当天快照」分支，删完拿出来的**还是继承自模板的 `true`** → 界面纹丝不动（现象 3）。
- 唯一会变的是趋势线，因为它直读数据库 —— 快照确实被删掉了（现象 3 的「只有趋势线变化」）。

### 模板的 `isCompleted` 是怎么变脏的

编辑对话框保存时执行的是 `task.copy(repeatRule = "daily", ...)`，**`isCompleted` 不在覆盖列表里，于是原值被原样保留**。
把一个「已经勾选完成的普通任务」改成「每日」，就把那个 `true` 一起写进了模板。

数据库里本来有一条同样的清理 SQL（`MIGRATION_8_9` 里 `UPDATE tasks SET isCompleted = 0 WHERE repeatRule != 'none'`），
但它**只在版本升级时跑一次**，管不了之后新写进来的值 —— 用户手机上那条脏模板就是这么来的。

### 改法：让「模板永远未完成」成为数据层不变式

| # | 位置 | 改动 |
|---|------|------|
| 1 | `data/FocusRepository.kt` | 新增 `normalizeRepeatTemplate()` / `isRepeatTemplate()`；`insertTask` / `updateTask` / `updateTasks` 写入前统一归一化，**重复任务模板一律清成未完成** |
| 2 | `data/FocusRepository.kt` | `getFocusStats()`、`getDailyCountsBetween()` 排除重复任务模板 —— 它的 `isCompleted` 是历史脏值，不该算成「完成过一次」，否则趋势线和统计虚高 |
| 3 | `TasksFragment.buildOccurrencesForDay()` | 虚拟实例显式 `copy(dueDate = day, isCompleted = false)`，当天完成与否**只由快照决定**。这一条同时兜住用户手机上已经存量的脏数据 |
| 4 | `data/AppDatabase.kt` | 新增 `MIGRATION_9_10`（数据库版本 9 → 10），跑一次 `UPDATE tasks SET isCompleted = 0 WHERE templateId = 0 AND repeatRule != 'none'`，抹平存量脏值，让「改回不重复」时不会突然冒出一个已完成状态 |

改动点 1 只作用于**模板**：快照行的 `templateId != 0`，不受影响，该是已完成仍是已完成。

**注意**：改动 1、2、3 里包含了「不重复任务 `isCompleted` 语义不变」的兜底条件，所以普通任务的勾选行为完全没变。

**2. 编辑任务会清空所有子任务完成状态**

- 位置：`TaskViewModel.updateTaskWithSubtasks()`
- 原逻辑：先 `deleteSubtasksByTaskId()` 删光，再逐条重插，而 `Subtask.isCompleted` 默认 `false`。
- 后果：用户哪怕只改一个标题，所有已勾选的子任务都会被静默重置，无任何提示。

**3. 「自定义锁机时间段」只生效一次**

- 位置：`LockAlarmReceiver`
- 原逻辑：`AlarmManager.setAlarmClock()` 是**一次性**闹钟，触发后没有重排。
- 后果：时间段只在设置当天生效，第二天起再也不锁，除非重启手机或重新保存一次设置。
- 修复：`ACTION_START` / `ACTION_END` 触发后立即调用 `LockMachineScheduler.applyAlarms()` 重排下一天。
  另外在 `applyAlarms()` 里加了 1 秒安全余量，避免闹钟刚刚触发就被判定为"还未到"而在同一秒内反复自触发。

**4. 锁机状态只存在内存，进程被杀后静默失效**

- 位置：`LockController`
- 原逻辑：`lockEnabled` / `timerRunning` 是两个内存静态变量。
- 后果：用户在任务管理器里划掉应用，重新打开时锁机状态变回 `false`，遮罩消失 —— 这是锁机类应用最忌的绕过口。
- 修复：改为从持久化数据推导 —— 用户开关存于 `TimerSettingsPreferences`（落盘），

- 同时明确：**暂停（PAUSED）依然算锁机生效**，否则按一下暂停就能临时解锁去刷别的应用。
- 并校验阶段结束时间，避免进程被杀后残留的过期 session 把用户永久锁在应用外面。

- 位置：`SettingsFragment.clearAllData()`
- 原逻辑：只清了 `focus_preferences` 和 `fortune_data`，然后 `deleteDatabase("focuslist.db")`。
- 后果：① 日记（`review_prefs`）、应用锁 PIN（`app_lock_prefs`）、主题、壁纸、锁机设置、

**6. 番茄钟用 `delay(1000)` 递减，息屏时计时漂移**

## v1.2.4（2026-09-03）

### 操作内容
尝试用 pull indicator 区域判断方案修复展开态日历滑动收起问题（用户反馈"没用"，后被 v1.2.5 替代）。

### 具体步骤

1. **问题背景**：v1.2.3 方案（expandState > 0.9f 时不拦截）用户反馈"还是会"。分析根因：CalendarView 横向滑动时可能内部判定为垂直手势，调用 `requestDisallowInterceptTouchEvent(false)` 把事件交回父容器，父容器随即拦截为垂直拖拽导致收起。

2. **方案——只有 pull indicator 区域开始的触摸才允许拦截**：
   * ACTION_DOWN 时记录 `downInPullArea`（`ev.y > height - 48dp`，底部三横线指示器区域）。

* 堆栈指向 `MaterialButtonHelper.loadFromAttributes` → `MaterialResources.getColorStateList`，即全局按钮样式的 `rippleColor` 属性加载失败。

1. 检查 `res/color/ripple.xml`，发现内容为 `<color name="ripple">#33FFFFFF</color>`。

* 根因：`res/color/` 目录要求文件必须是 ColorStateList（`<selector>` 根元素），不能是普通 `<color>` 资源。普通 `<color>` 应放在 `res/values/colors.xml`。MaterialButton 加载 `rippleColor="@color/ripple"` 时按 ColorStateList 解析，遇到 `<color>` 根元素抛 `Resources$NotFoundException`，导致任务清单页（默认首页）的 Button 渲染失败，应用启动即闪退。

1. 修复：将 `res/color/ripple.xml` 改为标准 ColorStateList：



```
\<selector xmlns:android="http://schemas.android.com/apk/res/android">

&#x20;   \<item android:color="#33FFFFFF" />

\</selector>
```



1. 检查 `default_text_color.xml` 和 `secondary_text_color.xml`，确认均为标准 `<selector>`，无同类问题。
